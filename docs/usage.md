# 使用说明

本文说明当前版本**实际可用**的功能，以及怎么用它们检查麦克风和调检测参数。安装与编译见 [build.md](build.md)。

> **当前可用范围：**
>
> - ✅ `replay` 离线检测：把 WAV 喂过真实的 DSP 链和检测状态机，打印事件与汇总。
> - ✅ Rust 测试套件：覆盖 DSP、检测器、门控、音频格式转换等约 90% 的逻辑。
> - ⬜ 桌面应用：能启动，但只有 Tauri 模板界面，没有接入音频引擎。
> - ⬜ 录音落盘与证据导出：`noise-store` 仍是骨架，**不会产生任何录音或报告文件**。

---

## 1. 桌面应用（当前只是外壳）

```bash
npm run tauri dev
```

会打开标题为「Anti-Noise — 楼上噪音监测」的窗口。窗口内容仍是 `create-tauri-app` 模板：点击「Greet」会调用 `greet` 命令，但 Rust 侧没有注册这个命令，会报错。

当前唯一存在的 IPC 命令是 `get_status`，固定返回：

```json
{ "state": "stopped" }
```

它只用来证明 Tauri 通路是活的，不反映任何真实监测状态。构建安装包、安装产物和平台注意事项见 [build.md](build.md) 第 6 节。

**不要用当前版本做取证或反击。** 它既不会采集音频，也不会写磁盘。

## 2. 离线检测：`replay`

### 2.1 它做什么

`cargo run -p noise-detect --example replay` 读取一个 WAV 文件，按检测器配置逐帧提取特征，再喂给与实时路径**同一份**检测状态机，打印：

- 每次事件开始、冲击确认、事件结束；
- 被冷却期或判据挡下的候选；
- 结尾的汇总统计。

它不访问声卡、不写文件、不发网络请求。滤波器状态跨帧连续，处理顺序与实时路径一致；这是「用录音调出来的参数能用在实机上」这个工作流的前提。

但它**不是**实时引擎：没有半双工门控、没有录音、没有回放。它只回答「这段录音如果实时跑，检测器会怎么判」。

### 2.2 准备录音

支持范围（由 `hound` 和示例代码决定）：

- 容器：**WAV**（不支持 m4a/aac/mp3/flac）；
- 编码：PCM 整型或 IEEE float；
- 采样率：任意（滤波器按文件采样率现场设计，不做重采样；低于 16 kHz 会打印提示，滤波器可能被钳位）；
- 声道：任意；多声道按**算术平均**降混成单声道，不是求和。

推荐：

- 48 kHz、单声道、24-bit PCM；
- 使用你打算实际监测的那支麦克风、那个位置和固定增益；
- 先录 30–60 秒安静背景，再出现目标声音——自适应底噪需要一段安静期才能站住；
- 关闭系统「音频增强」、自动增益、会议软件的降噪（见第 6 节）。

从手机录音转 WAV（可选，需自行安装 ffmpeg）：

```bash
ffmpeg -i input.m4a -ac 1 -ar 48000 -c:a pcm_s24le recording.wav
```

**内存注意**：`replay` 会把整段录音读进内存，48 kHz 单声道 1 小时约 1.4 GB（内部用 f64），立体声峰值更高。长录音请先切成 10–30 分钟一段。

### 2.3 运行

在仓库根目录：

```bash
# 基本用法
cargo run -p noise-detect --example replay -- 录音.wav

# 路径有空格：用引号
cargo run -p noise-detect --example replay -- "D:\噪音录音\2026-11-20.wav"

# 只看事件，不看逐帧门限与抑制明细
cargo run -p noise-detect --example replay -- 录音.wav --quiet

# 按真实时钟播放，适合对着现场同步观察
cargo run -p noise-detect --example replay -- 录音.wav --speed 1

# 全部参数
cargo run -p noise-detect --example replay -- --help
```

`--` 是 cargo 的参数分隔符：它前面的属于 cargo，后面的才传给示例程序。少了它，`--quiet` 之类会被 cargo 当成自己的参数。

`--help` 输出到 **stderr**，退出码 0；文件打不开、参数非法等错误退出码 1。

### 2.4 可覆盖的参数

默认值来自 `DetectorConfig::default()`。**只覆盖你理解的那一个**，其余保持默认。

| 参数 | 默认 | 作用 |
| --- | --- | --- |
| `--min-rise <dB>` | 15 | **主判据**：起始所需的最小帧间上升 |
| `--start-margin <dB>` | 15 | 起始门限高出底噪多少 |
| `--stop-margin <dB>` | 6 | 停止门限高出底噪多少（迟滞下阈值） |
| `--hangover <ms>` | 1500 | 电平跌破停止门限后的保持时间；决定相邻脚步是否合并成一个事件 |
| `--cooldown <ms>` | 2000 | 事件结束后的抑制期 |
| `--decay <dB>` | 10 | 确认冲击所需的衰减量；期限内不衰减就判为持续源 |
| `--lf-ratio <dB>` | 6 | 63 Hz 八度带相对 250–500 Hz 段的最小优势 |
| `--no-lf-ratio` | — | 关闭低频优势判据（麦克风低频差时用来排查） |
| `--crest <dB>` | 关闭 | 帧内峰值因数下限。**默认不要打开**，实测无法区分冲击与稳态隆隆声 |
| `--frame-ms <ms>` | 10 | 分析帧长。改动会改变帧率，并影响以帧计的参数（如 `rise_window_frames`）的含义；除非有明确理由否则不要动 |
| `--speed <N>` | 0 | 0 = 尽快跑完；1 = 按真实时钟；0 < N < 1 慢放，N > 1 快放 |
| `--cal-dbfs-at-94 <dB>` | 无 | 94 dB SPL 时的 dBFS 读数；给了就按 dB SPL 显示 |
| `--quiet` | 关 | 隐藏逐帧门限和被抑制的候选，只保留事件相关行 |

注意：`rise_window_frames`、`impact_confirm_ms`、`floor_tau_up_s`、`floor_tau_down_s` 等旋钮**没有**暴露成命令行参数，要改只能改 `crates/noise-detect/src/config.rs` 的默认值或临时改示例。完整旋钮表见 [detector-tuning.md](detector-tuning.md) 第四节。

### 2.5 输出怎么读

运行开头是文件信息：

```text
文件      <路径>
采样率    48000 Hz
声道      1（已降混单声道）
时长      123.45 s / 5925600 样本
校准      无 → 下面全部读作 dBFS（**不是**声压级）
提取      12345 帧 × 10.00 ms（实际帧长 480 样本，尾部丢弃 0）
```

- 「校准」决定 dB 的**零点**，不改变任何判据；
- 「提取」给出实际帧数、帧长和尾部不足一帧而丢弃的样本数；
- 采样率低于 16 kHz 或滤波器设计被钳位时，会额外打印 `⚠ DSP 降级`。

中间是逐条动作，时间戳相对文件开头：

| 行 | 含义 |
| --- | --- |
| `事件开始 #N` | 触发了一轮事件。显示触发时刻、触发带电平、当时底噪、超出起始门限多少 |
| `└ 冲击 #N` | **确认**了一次冲击：起音电平、确认期限内的峰值、衰减量。只有这一行代表「骤起后衰减」 |
| `事件结束 #N` | 显示时长、确认冲击数、被否决的候选数、类型（`Impact` / `Sustained`）、峰值 |
| `已抑制（冷却期）` | 冷却期内又来了触发，被挡下 |
| `已抑制（低频占比不足）` | 频谱判据认为不够低频，典型是语音/键盘 |
| `已抑制（峰值因数不足）` | 只有显式打开 `--crest` 才可能出现 |

`EventKind` 的分类依据是**事件期间有没有确认过冲击**：有冲击 → `Impact`；没有 → `Sustained`。空调启动、洗衣机这类「骤起后维持」会记成 `Sustained`，这是正确结果，不是漏报——它不会触发反击。

结尾是调参时真正要看的一屏：

```text
── 汇总 ─────────────────────────────────
触发带电平  最低 ...  最高 ...  平均 ...  （动态范围 ... dB）
起始判定    N 次
确认冲击    M 次（分布在 K 个事件里）
否决候选    R 次   ← 被当成持续源（空调/水泵）挡下的
事件占比    ...%（... s / ... s）
判据        上升 ≥ 15 dB  起始底噪+15  停止底噪+6  衰减 ≥ 10 dB
```

- **触发带动态范围**：先看这个。如果它比 `--min-rise` 还小，说明录音里根本没有足够的低频动态，调检测器没有意义，先查麦克风（[manual-test.md](manual-test.md) 第 0 节）。
- **起始判定 / 确认冲击 / 否决候选**：三个数一起看。事件很多但冲击为 0，说明全是持续源或判据没通过；否决候选在涨，说明持续源判据在工作。
- **事件占比**：事件总时长占录音的比例，用来判断「一段录音被记成噪声多久」。

### 2.6 常见判读

| 现象 | 优先怀疑 | 处理 |
| --- | --- | --- |
| 一次事件都没有 | 麦克风没录到 63 Hz，或 `min_rise_db` 太高 | 看动态范围；关判据对照：`--no-lf-ratio`；见 [detector-tuning.md](detector-tuning.md) |
| 起了事件但冲击 0 | 衰减不够，或低频占比判据过不去 | 试 `--decay 7`、`--lf-ratio 0` / `--no-lf-ratio` |
| 空调/车流也触发冲击 | `min_rise_db` 太低，或持续源确认期太短 | 调高 `--min-rise`；确认 `--decay` 没被调得过小 |
| 一次走动被拆成一串事件 | `hangover_ms` 小于脚步间隔 | 调高 `--hangover`（默认 1500 ms 已按 1 Hz 脚步设计） |
| 相邻两次无关撞击被并成一个 | `hangover_ms` 太大 | 调低 `--hangover` |
| 冷却期挡掉了真实的第二次撞击 | `cooldown_ms` 太大 | 调低 `--cooldown` |
| 稳态正弦/空调只有 `Sustained`，没有冲击 | 这是**设计行为** | 不需要处理；持续源不触发反击 |

### 2.7 调参顺序

每次只动一个旋钮，先压误报，再抓漏报，最后看底噪：

1. **压误报**：放一段只有空调/车流的录音，调 `--min-rise` 直到零事件；同时确认「否决候选」在涨，说明持续源判据在工作。
2. **抓漏报**：放一段有脚步的录音，确认每一步都产生 `冲击`，相邻脚步合并进同一个事件而不是刷出一串事件（调 `--hangover`）。
3. **看底噪**：放一段空调启停的录音，确认启动时不刷事件、停机后灵敏度能恢复。`floor_tau_*` 没有命令行开关，需要改配置默认值。

每次在实地发现新误报，就把它加成 `crates/noise-detect/tests/trigger_scenarios.rs` 里的一条场景。那是最终针对你这栋楼的特有回归套件。判据的完整推导和被实测推翻的假设见 [detector-tuning.md](detector-tuning.md)。

## 3. 校准：从 dBFS 到 dB SPL

未校准时，所有读数都是 **dBFS**（相对数字满刻度），**不是声压级**。软件不会假装知道绝对声压。

```bash
cargo run -p noise-detect --example replay -- 录音.wav --cal-dbfs-at-94 -28.0
```

含义：声校准器施加 **94 dB SPL @ 1 kHz** 时，这条录音链的读数是 **−28.0 dBFS**。程序据此把后续读数换算成 dB SPL 显示：

```text
校准      94 dB SPL = -28.00 dBFS → 下面全部读作 dB SPL
```

要点：

- **校准只改变 dB 的零点，不改变任何检测判据**——所有判据都是差值。
- 校准值只对**同一条录音链**（同一支麦克风、同一增益、同一系统设置）有效。换设备、改增益、开「音频增强」后都要重校。
- 没有声校准器时，可以用一段已知声源 + 声级计做粗略对照，但误差 ±5–10 dB，只能当参考。
- 94 dB SPL 校准器的标准流程、1 kHz 处 A 计权为 0 dB、自由场修正等细节，见 [acoustics-notes.md](acoustics-notes.md) 第四节。

如果当前没有实时电平表，可以用 Audacity 录一段校准器声音（同一麦克风、同一增益），读该段的 RMS dBFS，再把这个数传给 `--cal-dbfs-at-94`。录音过程中不要改系统增益。

## 4. 实机测试前的系统设置

这些设置会直接决定低频数据是否可用。

**Windows**

- 关闭麦克风的「音频增强」：设置 → 系统 → 声音 → 输入 → 设备属性 → 音频增强 → 关闭。
- 关闭通信设备的自动处理：不要同时开 Teams / Zoom / Discord 等会启用降噪、AGC、高通的程序。
- 采样率设为 48 kHz；避免 8/16 kHz 的通信设备模式。
- 允许桌面应用访问麦克风：设置 → 隐私和安全性 → 麦克风。
- 如果系统在 50–200 Hz 加了高通，检测器看到的信号已经被削掉——这不是调参能修的。

**macOS**

- 不要用蓝牙耳机做输入：会掉到 HFP 的 8/16 kHz，并叠加 AGC 和高通。
- 接通采集后需要在 `Info.plist` 提供 `NSMicrophoneUsageDescription`（当前配置还没有）。
- 内置麦克风的低频响应通常也有限；优先用低频响应明确的 USB 麦克风。

**通用**

- 麦克风放在能听到楼板声的位置，避开笔记本风扇、键盘和桌面振动。
- 固定输入增益，关闭自动增益。
- 正式调参前，先做 [manual-test.md](manual-test.md) 第 0 节的低频自检：50 Hz 与 1 kHz 在 63 Hz 带上的读数差应小于 20 dB。这一条不过，后面都是白费。

## 6. 数据与隐私（现状）

- `replay` 只读本地 WAV，不写文件、不联网。
- 桌面应用当前不采集音频、不写录音、不上传数据。
- `src-tauri/tauri.conf.json` 里预留了 `$APPDATA/anti-noise/sessions/**` 的 asset 协议范围，供将来前端播放事件录音；`noise-store` 实现之前不会创建或写入这个目录。
- 项目没有遥测或崩溃上报。

## 7. FAQ

**Q：`replay` 能起事件，但一次冲击都没有？**
先试 `--decay 7` 放宽衰减要求，再试 `--no-lf-ratio`。如果这样能出冲击，问题在麦克风低频响应或低频判据，不在上升沿判据。见 [detector-tuning.md](detector-tuning.md) 第五节。

**Q：一次事件都没起？**
先看汇总里的「触发带电平动态范围」。范围小于 `--min-rise` 时，录音里就没有可检测的低频动态，换麦克风/位置比调参有效。也可以先用 `--no-lf-ratio` 排除频谱判据。

**Q：为什么放 50 Hz 正弦没有冲击？**
稳态正弦没有「骤起后衰减」，会被判成 `Sustained`。这是设计行为。要验证链路，用敲击/脚步这类瞬态录音。

**Q：m4a / mp3 / flac 能直接用吗？**
不能。先转成 WAV（见 2.2 的 ffmpeg 命令）。

**Q：输出太快看不清？**
加 `--speed 1` 按真实时钟走，或 `--quiet` 只看事件；也可以重定向到文件：`... > replay.log 2>&1`。

**Q：路径里有空格或中文？**
用引号包住路径；`--` 仍然不能省。

**Q：为什么桌面应用没有监测界面？**
前端仍是 Tauri 模板，音频引擎的 `analysis.rs` 还没接进 `lib.rs`，`engine.rs` 尚未实现，`noise-store` 也还是骨架。当前只有离线检测可用。

**Q：能用它录音取证吗？**
不能。当前版本不会保存任何录音或证据文件。[manual-test.md](manual-test.md) 第 3、6 节描述的是将来存储层落地后的验证项。

**Q：replay 的结果和实时路径一致吗？**
设计上逐帧等价：同一个 `offline::extract`、同一份 `Detector` 实现、滤波器状态跨帧连续。但实时采集链路（`noise-audio`）目前还没接通，所以只有离线路径经过实际验证；接入后仍需按 [manual-test.md](manual-test.md) 做硬件在环对比。

**Q：为什么不能检测 31.5 Hz 以下？**
默认帧长 10 ms，31.5 Hz 一个周期 32 ms，帧内不足一个周期，任何基于帧内波形形状的判据都不可靠。检测器的主判据是帧间上升沿，不受这一点影响，但更低的频段需要更长的帧或包络检波。见 [detector-tuning.md](detector-tuning.md) 第二节。

**Q：长录音跑到一半内存爆了？**
`replay` 会整段读入内存。切成 10–30 分钟一段，或用单声道 48 kHz 以减少占用。

**Q：能不能直接改默认参数而不是每次都加命令行？**
可以，改 `crates/noise-detect/src/config.rs` 的 `Default` 实现；但默认值属于调参结论，改动前先看 [detector-tuning.md](detector-tuning.md)。
