# 硬件在环测试清单

零硬件可测的部分（`noise-dsp` / `noise-detect`，约 90% 的逻辑）由 `cargo test --workspace`
覆盖。**本文件只记录那些必须有真实麦克风、真实音响、真实房间才能验证的项目。**

每条都写明了「期望观察到什么」，因为「跑一下看看」不是测试。

---

## 0. 低频自检 —— 本项目的 go / no-go

**在做任何其他事之前先做这一条。**

楼板撞击声（脚步、拖椅子）的能量集中在 **20–200 Hz，峰值在 63 Hz 八度带**。
消费级笔记本麦克风和 MEMS 麦克风普遍在 20–50 Hz 以下滚降，Windows 的「音频增强」
和通信设备模式还会再叠一层高通 + AGC + 降噪。**如果麦克风把这个频段削掉了，
下游所有算法都是白费。**

| 步骤 | 操作 | 期望 |
|---|---|---|
| 0.1 | 手机在麦克风旁 10 cm 播放 50 Hz 正弦（用信号发生器 App） | 31.5 Hz 与 63 Hz 带明显抬起；125 Hz 以上几乎不动 |
| 0.2 | 手机播放 1 kHz 正弦，音量调到与上一步听感相同 | 500 Hz – 2 kHz 带抬起，低频带基本不动 |
| 0.3 | 用指关节敲地板/天花板，或跺脚 | 低频带出现瞬态；`trigger_band_db` 明显跳变 |
| 0.4 | 对比 0.1 与 0.2 的 63 Hz 带读数 | **差值应 < 20 dB。若 50 Hz 的反应远弱于 1 kHz，麦克风在低频滚降** |

**判定**：0.4 若失败（低频被削），停下，读 [README 的「已知限制」](../README.md) 和 [usage.md](usage.md) 第 4 节。
换传感器比调算法有用得多——优先考虑压电接触麦克风贴天花板。
**不要在没有通过这一条之前继续开发检测逻辑。**

## 1. 设备与采样率

| 步骤 | 期望 |
|---|---|
| 在设置页记下输入/输出设备的**实际达成** `StreamConfig`（采样率、缓冲、声道、格式） | 与设备属性页显示的一致；不是「你以为」的 48 kHz |
| 检查 63 Hz 带在 Windows「音频增强」开/关两种状态下的读数 | 差值 < 10 dB。若 > 10 dB，系统在加高通，App 应给出警告 |
| macOS：连接蓝牙耳机后开始监测，观察输入采样率 | 会掉到 8/16 kHz（HFP 模式）。App 必须警告并拒绝在 < 16 kHz 下运行 |
| 会话中途拔插 USB 麦克风 5 次 | 每次都能自动恢复，记录 `Degraded` 事件，不崩溃、不丢会话 |

## 2. 检测

| 步骤 | 期望 |
|---|---|
| 安静环境下静置 10 分钟 | 零误报；底噪 EWMA 平稳 |
| 正常说话、开关门、咳嗽 | 零误报或极少误报（视阈值） |
| 楼上真实脚步声出现 | 触发事件；事件开始时间不晚于实际声音 |
| 空调/风扇持续运行 30 分钟 | **零误报**——这是最重要的误报场景（连续低频 vs 冲击） |
| 汽车经过（若临街） | 低频突增但不触发。挡住它的是**持续源判据**（峰值因数默认已关闭，见 `detector-tuning.md` 第一节） |

**做这一节之前先做离线的**：录一段真实环境音，用 replay 跑一遍。

```bash
cargo run -p noise-detect --example replay -- 现场录音.wav
```

零硬件的等价测试在 `crates/noise-detect/tests/trigger_scenarios.rs` 里已经
覆盖了同样的判据组合（`cargo test -p noise-detect`）。实机测试要回答的是
**场景测试回答不了的那个问题：我的麦克风收到的信号，和合成信号像不像。**
如果录制文件里触发带的动态范围还不如 `min_rise_db` 大，那就不是检测器的
问题，回到第 0 节。

## 3. pre-roll 与录音完整性

| 步骤 | 期望 |
|---|---|
| 敲天花板触发一次事件，用 Audacity 打开事件 WAV | **瞬态不在样本 0**——前面必须有约 15 s 的可听 pre-roll。这证明环形缓冲的快照顺序和时间长度都正确 |
| 事件进行中从任务管理器强杀进程 | 之前每个已轮转的分段都能被播放器正常打开（头部已 finalize），丢失 ≤ 30 s |
| 硬杀后检查 `events.jsonl` | 仍是合法 JSONL（每行一条完整记录，无截断） |
| 对比 App 报告的 RMS 与 Audacity 对同一窗口的 RMS | 相差 < 0.5 dB。**这是不进实验室能拿到的最好的取证质量验证**——第二套独立的 dB 实现 |

## 4. 半双工与失控（**必须做，这是最危险的失效模式**）

| 步骤 | 期望 |
|---|---|
| 关闭回放，拍手 20 次 | 恰好 20 个事件，`suppressed_by_gate == 0`。**检测路径完全不受影响** |
| 开启回放、增益最小，拍手 | 每个事件恰好一次回放，无重触发 |
| **失控测试**：音响距麦克风 10 cm，增益调到最大，拍一次手 | 恰好 1 事件、1 回放。不是 2 个事件，更不是失控 |
| 同上配置，循环触发 100 次回放 | 恰好 100 个事件，不是 1000 个 |
| 跑耦合校准 | 报告的 `coupling_db` 与回放时观察到的麦克风电平相差几 dB 内 |
| 增益调到荒谬值 | L4 看门狗触发（> 12 次/分钟 → 自动停回放 + `Degraded(RunawaySuspended)`） |
| 回放期间检查录音 | 麦克风仍在录，WAV 段标记 `self_generated: true` |

### `suppressed_by_gate` 与 `frames_while_muted` 的区别（别搞混）

两个计数器量的不是一回事，**不要互相替代**：

- `suppressed_by_gate` —— 「**因为门控，我们漏掉了多少次真实的楼上噪声**」。
  它只在**冷却期**递增：那时检测器认为外面真有人，却被门挡下了。
  这是用户判断「反击功能是不是在牺牲取证能力」的唯一依据。
- `frames_while_muted` —— 「**自己的回放盖住了耳朵多久**」。回放期间
  检测器处于 `Suspended`，**只观测不判定**，所以它**不**递增
  `suppressed_by_gate`——那不是「漏掉的噪声」，是我们自己制造的。

所以验证 L1 硬静音看的是：回放期间 `events_started` **没有增加**，
且 `frames_while_muted` 与回放时长相称。不是看 `suppressed_by_gate`。

## 5. 长时间浸泡

| 时长 | 期望 |
|---|---|
| 10 分钟 | `dropped_in == 0`、无 cpal 错误、RSS 平稳 |
| 24 小时（每 10 分钟一次合成触发） | 磁盘线性增长、`dropped_blocks == 0`、RSS 平稳、事件计数精确 |
| 7 天 | 无内存泄漏、无句柄泄漏、每日事件计数断言通过 |

## 6. 取证质量

| 步骤 | 期望 |
|---|---|
| 未校准时检查 UI 标签 | 明确标注 `dBFS` 或 `dB SPL (uncalibrated)`，**绝不**声称绝对声压级 |
| 用 94 dB @ 1 kHz 声校准器校准后复查 | 与校准器读数相差 ±0.5 dB 内（校准器本身有 ±0.3/±0.5 dB 等级差） |
| 导出一夜的报告，`sha256sum` 对照 `session.json` | 一致 |
| 打开 `report.md` 核对时间戳与 WAV | 一致 |

**绝对声压级**：没有声校准器就不能声称绝对的 dB SPL。
未校准的手机 SPL App 典型误差 ±5–10 dB，只能做粗略对照。
真要做法律用途，94 dB @ 1 kHz 声校准器（约 ¥1000）是唯一能让 dB SPL 主张站得住脚的东西。
