# 检测器调参

本文件记录**每个判据为什么存在、以及它到底有没有用**。默认值只是起点，
真正的调参要用你自己楼里的录音跑 replay（见文末）。

---

## 一、已实测推翻的判据：帧内峰值因数

计划里曾把「帧内峰值因数」当作区分冲击与稳态噪声的核心特征，阈值
`min_crest_db = 8`。**实测证明这条路走不通。**

48 kHz、10 ms 分析帧下的实测值：

| 信号 | 帧内峰值因数 | 帧间上升（相对前 50 ms） |
|---|---|---|
| 冲击，1 ms 宽 | 10.00 dB | 110.0 dB |
| 冲击，10 ms 宽 | 0.00 dB | 120.0 dB |
| 稳态隆隆声（30 Hz 带宽） | **9.99 dB** | **4.6 dB** |

复现：
`cargo test -p noise-dsp frame_crest_cannot_separate_rumble_from_impulse_but_rise_can -- --nocapture`

### 为什么

63 Hz 的周期是 16 ms，**比 10 ms 的分析帧还长**。帧内装不下一个完整周期，
「峰值/有效值」于是退化成「这段波形碰巧落在周期的哪个相位」——它在
0–10 dB 之间随机跳动，与信号是冲击还是连续**无关**。

用 `min_crest_db = 8` 会得到最糟的结果：**把最需要拦住的稳态隆隆声放行**
（实测 9.99 dB > 8），同时把 10 ms 宽的冲击漏掉（0.00 dB < 8）。

### 结论

**检测器的主判据是帧间上升沿，不是峰值因数。**

上升沿在两种信号上差了 100 dB 以上，判别力是压倒性的。这也解释了为什么
`AdjustedNoiseFloor` 的自适应速度必须是**升快降慢**：底噪快速跟上持续噪声，
才是抑制空调/车流这类误报的第一道防线。

`min_crest_db` 保留为可配置项但**默认不参与判据**（设为 0 = 关闭），
仅在事件记录里留下 `crest_db` 供事后审阅。

## 二、帧长与目标频率的关系（选帧长的依据）

| 中心频率 | 周期 | 10 ms 帧内的周期数 |
|---|---|---|
| 31.5 Hz | 32 ms | 0.31 |
| **63 Hz** | **16 ms** | **0.63** |
| 125 Hz | 8 ms | 1.25 |
| 250 Hz | 4 ms | 2.5 |

**10 ms 帧在 63 Hz 以下不足一个周期。** 这带来三个后果：

1. 任何「帧内波形形状」类判据（峰值因数、过零率、波形不对称度）在
   63 Hz 以下都不可靠——上面那张表就是原因。
2. 低频电平的帧间估计本身噪声很大，所以 `rise` 判据必须相对一个**窗口**
   的最大值，而不是单独前一帧，否则会被单帧的估计噪声触发。
3. **上升沿那一帧自己的电平估计不可信**，见第三节。窗口取在哪里、
   比较用哪一帧，都不是细节——取错了会系统性地漏掉每一次真实脚步。

如果将来要检测 31.5 Hz 以下的成分，帧长必须加长或改用包络检波，
不能沿用 10 ms。

## 三、上升沿判据的三个偏差（全部实测）

`rise` 是主判据，但它一开始的写法在三处偏了，三处**叠加**的结果是
「+25 dB 的突发只量出 14.6 dB 的上升」——差 0.43 dB 没够着 15 dB 的门限。
这不是精度问题，是判据在真实信号上根本不成立。三条偏差各自独立，
必须各自补偿。

### 3.1 突发**第一帧**的电平被压低约 7 dB

滤波器从全零状态起步时低估能量，这一点原先只在「会话第 0 帧」被认识到。
**实际现象更普遍：任何一次突发的起音帧都低 7 dB 左右**——因为突发之前
滤波器一直在处理安静信号，状态接近零，与刚上电时无异。

48 kHz、80 ms 63 Hz 突发（场景 7）：

```text
t=3000 ms   -41.76 dB   ← 起音帧，被低估
t=3010 ms   -34.30 dB
稳态         -34.5 dB
```

触发带的 20 Hz 高通要几十毫秒才稳定，而**上升沿判据恰好落在这唯一一帧
不可信的电平上**。补偿办法是把判据挪到下一帧去量，见 3.4。

### 3.2 `max` 是「最近电平」的有偏估计

窄带源（1–2 个自由度）的帧级电平标准差有 3–4 dB。取 5 帧的**最大值**，
得到的不是均值也不是中位数，而是分布的上侧：

```text
标称 min_rise_db = 15  →  实际要求约 15 + 3 = 18 dB 的真实超出量
```

这个偏差方向是**保守**的（导致漏报而非误报），所以在压误报的调参里
不会暴露出来，只会让人觉得「检测器怎么这么迟钝」。

### 3.3 八度带滤波组比触发带滞后一帧

起音帧上 `lf_ratio` 还没收敛：

```text
t=3000 ms   lf_ratio = -0.60 dB   ← 起音帧
t=3010 ms   lf_ratio = 18.59 dB   ← 一帧之后才成立
```

在起音帧上判低频占比，会把**每一次真实脚步**都否掉。而且否掉之后电平
已经上去了、不再有新的上升沿，所以**不会重试**——这不是「偶尔漏一个」，
是系统性全漏。`sm.rs` 因此用 `PendingOnset` 把起始判定延后一帧：电平与
时间戳取自上升沿那一帧，频谱判据取出结果的那一帧。

### 3.4 修好的形式：延后一帧量上升，基线固定

```text
rise = max(db[j-1], db[j]) − max(db[j-6] .. db[j-2])
```

- 被测量的是**已经稳定**的那一帧（`db[j-1]`），回避 3.1
- 分母窗口 `[j-6..j-2]` **完全落在突发之前**，不含任何突发帧，回避 3.2
- 同一突发：14.57 dB → **22.0 dB**，判据重新成立

代价是判定晚 10 ms。对「反击约 100 ms 准确」的延迟预算无关紧要。

### 3.5 滑动的基线**无法**区分单帧毛刺和真实突发

一个看起来显然的改进是「要求上升沿持续两帧以上」。它不成立：

`[j-6..j-2]` 这个窗口**把刚过去的 `j-1` 排除在外**，所以单帧毛刺和
六帧突发都会**恰好产生两个连续的上升沿判定**。等到毛刺进入基线时
（`j+3`），`onset` 早已回落，判据已经错过它了。

所以基线必须**在上升的那一刻固定下来**（`PendingRise`），下一帧再确认
电平是否仍站在上升之后的高位上：

```text
              基线（固定）    第 1 帧     第 2 帧     判定
单帧毛刺        -60          -45  ↑      -60        结束得太快 → 否决
真实撞击        -60          -45  ↑      -42        还在高位   → 确认
```

这不是理论推演——场景 4 的 60 秒空调声（低频主导、稳态）在没有这道
确认时**会确认出一次「冲击」**，而冲击会被 `warrants_response()` 放行，
直接导致对着一直响的空调反击。

### 3.6 衰减也要同样确认一次

`PendingRise` 的镜像问题：**持续源的起始阶跃会先冲过头再凹下去**。
`start_event` 记下的 `onset_db` 是冲高的顶，紧接着一帧掉下去，看起来
和真衰减一模一样。场景 4 的 +25 dB 隆隆声：

```text
t/ms     -60 帧基准    5010      5020      5030      5040
dB     -63.8         -44.0     -44.3     -55.8     -42.0
                                          ↑ 低 11.8 dB，越过 decay=10
```

5040 那一帧就弹回去了，说明 5030 是个缺口而不是衰减。所以衰减同样
延后一帧确认（`PendingDecay`），判据是「**还在低位**」。

真实的撞击掉下去之后不会马上弹回——下一声脚步之前房间回到环境级。

### 小结：判据的完整形态

```text
一帧电平 ──┬─→ 上升且越过 stop_db ──→ 记下固定基线 ──→ 下一帧仍高？ ──→ 候选
           │                                                          │
           │                                            下一帧已衰减？ ──→ 冲击
           │                                                          │
           └──────────────────────────────────── 期限内没衰减 ──→ 否决（持续源）
```

上升、衰减**各自**都要跨两帧确认；中间的「候选挂起」是唯一允许
单帧就下结论的地方（因为它的结论是「再等等」）。

## 四、旋钮清单

| 旋钮 | 默认 | 作用 | 调大的后果 |
|---|---|---|---|
| `start_margin_db` | 15 | 起始阈值高出底噪多少 | 漏报轻微脚步 |
| `stop_margin_db` | 6 | 迟滞的下阈值 | 事件拖尾变长 |
| `min_rise_db` | 15 | **主判据**：上升沿最小增量。见第三节，实际要求约 +3 dB 的真实超出 | 漏报缓慢的拖拽声 |
| `rise_window_frames` | 5 | 上升基线跨几帧（50 ms） | 基线变旧，缓慢渐强的声音被当成突发 |
| `min_lf_ratio_db` | 6 | 63 Hz 带比 250/500 Hz 段高多少 | 麦克风低频差时全面漏报 |
| `min_impact_decay_db` | 10 | 确认冲击所需的衰减量 | 冲击确认变慢，可能掉进否决 |
| `impact_confirm_ms` | 500 | 期限内不衰减即判为持续源 | 空调类误报变多 |
| `hangover_ms` | **1500** | 事件内两次冲击的最大间隔 | 把无关的两次撞击并成一个事件 |
| `cooldown_ms` | 2000 | 事件结束后的静默期 | 漏掉连续的第二次撞击 |
| `floor_tau_up_s` | 30 | 底噪上升的时间常数 | 空调启动后误报窗口变长 |
| `floor_tau_down_s` | 300 | 底噪下降的时间常数 | 空调停机后灵敏度恢复慢 |
| `min_crest_db` | `None`（关闭） | 见第一节，**不要打开** | — |

`hangover_ms = 1500` 而不是 800：**它必须大于你想合并的最慢脚步间隔**。
1 Hz 的脚步（间隔 1000 ms）在 800 ms 下会被切成两个事件，第二个紧接着
被 `cooldown` 挡掉——一次走动只记到一半，而漏掉的那几步在证据里就是
「不存在」。

**默认值来自理论，不要当作答案。** 63 Hz 峰值、15–40 Hz 楼板共振、
空调底噪、楼板是混凝土还是木结构，都会改变上面的数字。

## 五、调参回路

```bash
cargo run -p noise-detect --example replay -- neighbor.wav
cargo run -p noise-detect --example replay -- neighbor.wav --min-rise 12 --hangover 2500
cargo run -p noise-detect --example replay -- neighbor.wav --quiet
```

把 WAV 喂过**与实时路径逐帧等价的**提取 + 检测路径，打印 action 流与
汇总。`--help` 列出全部可覆盖的旋钮。默认尽快跑完（约 50× 实时），
`--speed 1` 按真实时钟走。

结尾的「汇总」才是调参时要看的那一屏——单个事件的细节会骗人，
「这段录音里有几次事件、几次被当成持续源否决」不会。

调参顺序（每次只动一个旋钮）：

1. **先压误报**：放一段只有空调/车流的录音，把 `min_rise_db` 调到零事件。
   看汇总里的「否决候选」——那个数在涨，说明持续源判据在工作。
2. **再抓漏报**：放一段有脚步的录音，确认每个脚步都触发，且相邻脚步
   合并进同一个事件而不是刷出一串事件（调整 `hangover_ms`）。
3. **最后看底噪**：放一段空调启停的录音，确认启动时不刷事件、停机后
   灵敏度能恢复（调整两个 `floor_tau_*`）。

**如果一次事件都没起，先看触发带电平的动态范围，而不是先动旋钮。**
范围还没判据大，说明麦克风压根没录到那个频段——那是硬件问题（麦克风低频滚降），
调检测器只会把噪声当成脚步。

### 麦克风存疑时的第一件事

```bash
cargo run -p noise-detect --example replay -- neighbor.wav --no-lf-ratio
```

低频占比判据在低频响应差的麦克风上会否掉一切。关掉它跑一遍：如果
事件和冲击冒出来了，问题在麦克风而不在检测器；如果还是没有，才轮到
调 `min_rise_db`。

## 六、尚未有数据回答的问题

- `min_rise_db = 15` 在你房间里够不够？房间混响会不会把瞬态抹平？
- 15 s pre-roll 够不够捕捉前奏，还是邻居的模式需要 30 s？
- 楼板的低频阶跃响应会不会改变理想的 `hangover_ms`？
- 拍手（宽带、快衰减）和踩地板（窄带、慢衰减）需不需要两套参数？
- 第三节的 3.2 那个「+3 dB」是在 63 Hz 窄带噪声上量的。真实脚步声的
  带宽更宽、帧间起伏更小，偏差可能小于 3 dB——**它到底是多少，取决于
  你自己楼里的脚步频谱**，不是常数。

每次在实地发现新误报，就往 `crates/noise-detect/tests/trigger_scenarios.rs`
加一条场景。**那个文件最终会成为针对你这栋楼特有的回归套件**——
比任何通用默认值都值钱。它现在已经覆盖了本节第三到第六小节的全部
偏差：突发、稳态隆隆声、频谱平坦的低频源、冷却期、静音期、门控缺席。
